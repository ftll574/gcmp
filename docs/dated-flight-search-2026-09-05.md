# 指定日期航班查詢：實作與啟用紀錄

日期：2026-09-05。工作區：`E:\workspace\gcmp`。

## 目標與目前狀態

依使用者要求，產品提升為「選航段 → 查可飛日期 → 看當日營運班次 → 加入行程 → 向客服問獎勵機位」，不做可兌換座位查詢。

**軟體介面、資料驗證、第一個班表供應商接入程式與本機服務已實作；正式班表供應商尚未連線，也沒有付費帳戶驗證。** 檢查時 DevSpace 執行環境未設定 `CIRIUM_APP_ID`、`CIRIUM_APP_KEY`、`VITE_SCHEDULE_API_BASE`。不能把本輪測試成功宣稱為全球航空班表已可查詢。

## 已完成的使用流程

- 航線探索器的每個目的地有「查可飛日期」，也能直接輸入有效的目的地 IATA，不必先等有限航網目錄收錄該機場對。
- 月曆由使用者明確按下查詢，不會在載入所有航線卡時自動產生大量供應商請求。每次最多 31 天，同一機場對的結果可在不同營運航空篩選條件下重用。
- 月曆分為「有班次」「無符合班次」「未知」。正面結果必須含明確營運航空、航班號與當地起降日期時間；負面結果另外必須是完整且未過期的回應。錯誤、缺憑證、過期、部分資料與超出範圍都不會變成無班次。
- 每天列出營運航班號與起訖機場當地時間。跨午夜或換日線時保留兩端完整日期；不拿兩個不同時區的當地時刻直接相減。
- 可選擇航班連同日期加入行程，或對既有航段重新查詢並替換。單段資料可複製給客服；文案明示仍需查獎勵機位與開票規則。
- 分享網址新增可選 `fn=` 參數，保留營運航班號尾碼；日期與營運航空仍使用原 `d=`／`op=`。不保存「已查證」標籤或查詢憑證。重新載入後標示已存參考、班表須重查。更改日期／航空／切成地面交通時清除舊航班號；停留修改不會刪掉它。
- 舊每週班表只作參考，不會填入新月曆的已確認狀態，也不再鎖住 App 的手動日期編輯。舊版不符警告改成「每週參考與日期不符，請再查當日班次」，不直接宣稱當天停飛。

原 138 筆週班表與 42 筆航網觀測未被改造成虛構的日期航班。所有新增日期測試資料都位於 `tests/fixtures/`，標示 synthetic，沒有放入正式 `public/data`。

## 供應商接入與限制

第一個 adapter 採 Cirium FlightStats Schedules 的 route/departure/date 介面。正式文件表示依航線／機場查詢屬 Contract 方案；只有依航班號查詢是另一個授權層級。正式啟用前需確認可用端點、未來查詢範圍、對外展示／快取權限與費用，不把一般免費帳戶假設成擁有全航線查詢。

官方參考（2026-09-05 查閱）：

- `https://developer.cirium.com/apis/flightstats-apis/schedules`
- `https://developer.flightstats.com/api-docs/scheduledFlights/v1/scheduledFlightResponse`
- `https://www.cathaypacific.com/cx/en_KH/book-a-trip/timetable.html`

國泰上述 timetable 頁面明示售完航班不顯示，因此不能把它的搜尋空結果當成航班不存在。第一版沒有使用售票結果、歷史機率或社群轉錄來冒充完整的日期班表。

供應商 adapter 可替換；沒有替使用者購買 Cirium 或鎖定長期供應商。本輪亦未呼叫需要費用的外部班表服務。

## 本機啟用方式

先取得有相應授權的憑證，將 `.env.schedules.example` 複製為 **`.env.schedules.local`**，只在本機設定：

```dotenv
CIRIUM_APP_ID=your-server-side-app-id
CIRIUM_APP_KEY=your-server-side-app-key
SCHEDULE_PORT=8787
SCHEDULE_DAILY_BUDGET=200
SCHEDULE_ALLOWED_ORIGINS=http://localhost:5173,http://127.0.0.1:5173
```

請勿把真正憑證貼到聊天、提交 Git 或加上 `VITE_` 前綴。既有 `.gitignore` 的 `*.local` 已涵蓋本機設定檔。

另在前端 `.env.local` 設定公開服務位置（這個值不是秘密）：

```dotenv
VITE_SCHEDULE_API_BASE=/api
```

兩個終端機分別執行：

```text
npm run schedules:serve
npm run dev
```

Vite 將 `/api/schedules` 代理到 `127.0.0.1:8787`。健康檢查為 `http://127.0.0.1:8787/api/schedules/health`，只顯示是否設定供應商，不回傳任何密鑰。

**沒有憑證時服務也可啟動，但只回傳 unknown／not-configured，不會回傳測試班次。** 前端 base 未設定時查詢按鈕停用並顯示尚未連線，避免誤導。

## 正式部署與成本保護

現有靜態前端仍可建置與使用，不強迫把整站改成後端框架。新增 Node gateway 必須另外部署在有 TLS 與反向代理的環境，前端建置時指向其 HTTPS `/api` base；僅把前端部署到原 GitHub Pages 不會自動啟用後端。

目前保護：憑證只用伺服器端 header、固定供應商網域、禁止跟隨重新導向、上游 8 秒逾時、2MB 回應上限、最多 4 個併發、同機場對／日期合併請求、15 分鐘結果期限、最多 1,000 筆記憶體快取、最多 128 個排隊日期、每 IP 每分鐘 10 個 HTTP 請求、預設每個服務程序每日 200 次上游請求。查一次完整月份可能需要最多 31 次上游呼叫，並非必然只計一筆供應商交易；重查在有效快取內會重用結果。

本機服務只綁定 loopback。CORS 白名單不是身分驗證，也不能防止非瀏覽器濫用。正式公開服務仍須設置邊緣限流／濫用防護；多程序或多副本部署前必須以持久化共享儲存集中管控額度，不能把目前的每程序計數當成全站費用保證。更改快取期限需與授權條款一致。
